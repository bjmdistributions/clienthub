Warehouse sheet to sellable lot

How the lot builder turns a raw 144,635-row warehouse manifest into priced, pickable lots — and what you have to get right to rebuild it.

Input rows144,635
Canonical stacks96,834
Distinct products15,217
Units179,672
Locations7,680
MSRP$17,074,851

01The two rules

Rule one — the lot

A warehouse location is all or nothing. If a slot is worth taking for its Nike, every other brand in that slot comes too.

Rule two — the product

Two rows typed differently are two products. Always. Same barcode, same brand, doesn't matter.

The buyer reads the title. Nothing may silently rewrite it.

Everything downstream is a consequence of these two. Both are counter-intuitive, and both were learned by getting them wrong first.

Why rule one

A SKU-level allocator was built first. It answered "give me 676 Nike" perfectly and produced a lot spread across 3,545 pick slots. Nobody can pull that. The atom must be the location, because the location is what a person walks to.

  • Filters do not select items. They rank and qualify locations.
  • Adding a location takes 100% of its contents, including brands you did not ask for.
  • "Only footwear" cannot mean "filter out the apparel". It has to mean "only show slots containing nothing but footwear".

Why rule two changed in rev 2

Revision 1 collapsed differently-typed titles within a brand, on the theory that they were the same shoe worded twice. Of the 2,154 titles it merged, only 60 were the same text with different punctuation. The other 2,094 — 16,551 units — were genuinely different wording, and at least one pair was a different shoe:

Barcode 197968446084
  380 units   New Balance 9060 Big Kid Shoes, Great Plains/Twilight Haze, Size 6.5
    1 unit    New Balance 550 - Men's (Navy/Electric Sky) Size 12

Merging relabelled the 550 as a 9060. No rule can reliably separate a re-wording from a different model, so no rule should try.

The trade, stated plainly

Removing the merge took 96,675 stacks to 96,834 and 13,063 products to 15,217. The same shoe can now appear twice in a manifest under two names. That is correct: a duplicate line is a cosmetic annoyance, a relabelled line is a dispute.

02Data model

Input

Six columns. Everything else is ignored. Column order does not matter; the header row may sit below junk rows.

ColumnTypeNotes
UPC/EANstringNever parse as a number — leading zeros and 13-digit codes both break
LocationstringFree text in practice. See stage 2
Box #string82% empty. Only meaningful inside its own location
RemainingintUnits on this row. Rows repeat per scan
Titlestring8% empty. Carries brand, model, gender, size — all unstructured
MSRPmoneyMay carry $ and commas

Canonical row

The pipeline collapses input rows into stacks. One stack is one product sitting in one slot.

stack {
  location   "43-127-04A"     // canonical ZZ-RRR-SS[A-D]
  box        "BOX3" | ""      // scoped to the location
  upc        "196969506827"
  title      "Nike Air Max ..."   // exactly as typed. never rewritten
  units      46
  msrp       190.00
  brand      "Nike"           // all four derived from title
  category   "Footwear"
  segment    "Kids"
  size_us    6.5 | null
  desc_known    1 | 0         // quality flags, see section 05
  title_risk    0 | 1 | 2 | 3
  upc_ambiguous 1 | 0
}
The key that matters

The stack key is (location, box, upc, title). Two products under one barcode must stay two rows, and the title is the only thing that separates them. 12,452 barcodes resolve to 15,217 products.

Derived hierarchy

Locations parse as ZZ-RRR-SS[A-D] — zone, rack, shelf, sub-slot. Slicing the canonical string gives you the pick path for free, and sorting by it is a warehouse walk in aisle order.

LevelSliceCountMedian units
Zone[0:2]16—
Rack[0:6]385412
Locationfull7,68017

Median location holds 17 units at about $1,875 MSRP; 90th percentile is 38; the largest is 697. That spread is why lots are built by adding slots one at a time rather than by splitting a target evenly.

01Drop what isn't inventory before anything else

Totals rows. Exported sheets frequently end with a SUM() row: no UPC, no title, and a Remaining equal to the entire sheet. One such row doubles your inventory. Detect as UPC is empty, drop, and report the phantom units by name so it's visible rather than silent.

Approval flags. Order sheets often carry an extra column of yes/no. Detect any non-required column whose non-empty values are all in {yes,no,y,n,true,false,x}, and drop the negatives.

02Normalise locations 8,250 spellings → 7,680 slots

The highest-leverage stage in the system. The same physical shelf appears under many spellings; unmerged, your inventory fragments into slots that don't exist.

43-127-01B   43 127 01b   43'127'01B   43--127-01B
43-127--01B  43-12701B    43-11O-03A   ← letter O for zero

The repair ladder, in order:

  1. Uppercase and trim.
  2. If the string contains O/I/L and swapping them for 0/1/1 leaves something purely numeric, take the swap.
  3. Collapse every run of non-alphanumerics to a single space.
  4. If fewer than three parts remain, try to split a glued run: 4312701B → 43 127 01B.
  5. Match (\d{1,3}) (\d{1,4}) (\d{1,3})([A-D]?), zero-pad to ZZ-RRR-SS[A-D].
  6. No match → mark unparsed and exclude from lots. Never guess.

Emit a raw→canonical map as an artifact. It is how you audit an unexpected merge, and how the warehouse finds spellings worth fixing at source.

03Backfill missing titles 11,403 blank → 2,714 unknown

8% of rows have no description. The same barcode is usually described on another row, so build a UPC→title catalogue from the rows that have one and fill from it. That recovers 76%.

This is the only place a barcode decides what a title says, so record it: every filled row gets title_risk 1 or 2, and every unfillable row gets 3. Section 05 covers what those mean.

04Grade barcodes — merge nothing rewritten in rev 2

Do not collapse titles. Classify a provisional brand per title and use it only to grade the barcode, never to rewrite anything.

A barcode whose rows disagree on brand is conflicted. But a conflicted barcode is usually a typo, not an ambiguity: 89% of them are a single stray unit against hundreds. Only flag upc_ambiguous when the runner-up product is at least 3 units and at least 5% of the barcode.

BarcodesShapeTreatment
999a single stray scanconflicted, not flagged
739one brand under several namesnot conflicted — separate products
131mixed brands, small numbersconflicted, not flagged
38two brands in real quantityupc_ambiguous = 1, 1,586 units

Also emit every barcode carrying two or more product names (1,907 of them, 77,740 units) with all its names. That table is what the conflicts screen in section 10 renders.

05Resolve prices one product, one price

Group by exact title and take the modal price. Backfill $0 rows from the same UPC. Then level: every stack of the same product carries the same price.

Two bugs worth pre-empting

Grouping on empty titles. If blank titles are included, every undescribed row becomes one pseudo-product and gets stamped with its modal price. That fabricated $45,335 of MSRP. Exclude empty titles from price resolution.

Skipping the levelling pass. Without it a stack whose rows were all $0 keeps 0 while a sibling stack of the same product carries the real price, and the UI's per-product index then disagrees with the pipeline's own total.

06Classify see section 04

Derive brand, category, segment and size from the title. Do this once per distinct title (~15,000) and join, never once per row (145,000).

07Roll up to stacks 144,634 → 96,834

Group by (location, box, upc, title), sum units, take the worst title_risk in the group. Drop rows whose location never parsed. Sort by location so the location index can be a contiguous range per slot — that single choice is what makes re-ranking 7,680 locations on every keystroke imperceptible.

04Classification

Everything the buyer filters on is inferred from one unstructured text field. The dictionaries matter less than the resolution order.

Brand: literal beats silhouette

  1. Literal names. If the title spells exactly one known brand outright, that wins. No further checks.
  2. Model names. Otherwise fall through to silhouette patterns — samba, air max, chuck taylor, 9060, classic clog.
Why the order is not optional

WMNS is Nike's own women's prefix, so it sat in the Nike pattern list. This data uses it generically, and Nike was checked before adidas — so "adidas Sambae WMNS Sneakers" classified as Nike. 32 titles, 707 units, invisible until someone cross-checked a brand total against a spreadsheet filter.

Roughly 1,700 units of Crocs carry no literal brand at all — they are titled "Classic Clog K Lagoon J6" or "Gothic Punk Love Jibbitz Pin Set of 5". Tier 2 catches them, which is why a plain text search undercounts a brand by 30%.

Category cascade

First match wins; non-footwear is tested first, because a shoe title rarely says "coverall" but an apparel title often says "crew" or "low".

socks → underwear → apparel-bottom → apparel-top → bag → headwear
      → accessory → boots → sandals → clogs → slippers → cleats
      → footwear keyword or silhouette   → Footwear
      → apparel size marker (2XL, W42 x L36) → Apparel-Other
      → a parseable US shoe size        → Footwear
      → Uncategorized

The last two fallbacks matter: 43% of titles carry no category word at all, and the size test alone rescues most of them. Residual Uncategorized is 6%.

Size

Five ordered patterns — 9.5 US, Size 11, trailing , 7.5 M, 10 M, 7Y. Accept only 0.5–20 to reject EU sizes and style numbers. Apply case-insensitivity to every pattern; one of the five was missing the flag, so lowercase Size 6w never matched.

Keep one source of truth

If the system has both a server-side cleaner and a client-side one, do not maintain two copies of these tables. Define them once and serialise them into the client at build time. Write every pattern in the intersection of Python re and JavaScript RegExp — no named groups, no lookbehind, no inline flags — so the same strings compile in both.

05What the manifest vouches fornew in rev 2

The buyer reads the description, not the barcode. So the description is what gets graded, and the grade travels all the way to the manifest.

Only grades 2 and 3 can mis-describe a lot, and together they are 3% of stock. A typical 3,000-unit lot lands at 2,967 typed / 32 soft / 4 to verify — a handful of lines to eyeball, not a wall of noise.

Grade the right object

Revision 1 warned on upc_ambiguous, which flagged 6,338 units in a lot and was mostly noise — a barcode being reused does not touch a row whose title was typed by a human. Grading the description instead cut the real exposure to 2,014 units and made the warning actionable.

06Lot engine

The whole engine is a ranking over locations plus a set of chosen ones. No allocation, no optimiser.

Two filters, not one

FilterFieldsJob
WANTbrand, size range, MSRP rangeRanks slots. Excludes nothing
ALLOWcategory, segment, described-only, brand-lockDecides which slots qualify at all

WANT is always a subset of ALLOW. Collapsing them into one filter is wrong in both directions:

Query: Nike + footwearSlotsProblem
One filter, no strictness4,4771,921 of them contain apparel
One filter, strict179Demands 100% Nike footwear; discards a slot that's 95% Nike + 5% adidas
Two filters, strict2,449Slots holding nothing but footwear, ranked by Nike content

Ranking

for each location L not already picked or removed:
    total   = sum(units in L)
    allowed = sum(units in L matching ALLOW)
    want    = sum(units in L matching WANT)      // WANT is a subset of ALLOW
    breaks  = total - allowed

    if ALLOW is set and breaks / total > slack:  skip
    if WANT  is set and want == 0:               skip
    emit { L, total, want, breaks, pct: want/total }

sort by pct desc            // concentration, the default
     or want desc           // volume

slack is the one dial: the share of a slot allowed to violate ALLOW. Zero is strict. It is the honest expression of "I'd take a little apparel to get more volume".

Surface what the sort costs

Sorting by concentration puts tiny slots on top — of the top 100 by percentage the median slot is 8 units, and the whole top 100 totals 1,100 units. Sorting by volume gets 1,940 units from the same 100. Ship a minimum-size input and say which trade the current sort is making.

What a card must show

Because the take is all-or-nothing, the decision needs the whole slot visible before the click, not after:

43-127-04A                                  96% of it
48 units · 10 styles · $4,690 MSRP · 46 you want
  Nike         ####################  46
  New Balance  #                      2
  Comes with 2 other units: New Balance 2
  [ Add whole location → ]

The "Comes with" line is the single most important element in the interface. Aggregate it too: taking all 2,449 slots in that query brings 12,865 Nike units inside 44,563 total — about 2.5 units of something else for every unit you wanted.

Live selection totals

When several categories are ticked, show the combined figure. Tick Footwear, Boots, Sandals, Clogs, Slippers and Cleats and the panel reads Total 131,978 · $13,436,733. Count available stock only, so the total drops as slots are staged and removed.

07Outputs

Three artifacts, three audiences. They must reconcile to the same unit total or none of them can be trusted.

ArtifactForContains
ManifestBuyerHeader totals, brand counts, locations, then every line with UPC, description, brand, category, segment, size, MSRP, qty, extended, Description check
Brand countsSalesBrand → units, % of lot, styles, MSRP, and how many locations hold it
Pull sheetWarehouseLocation → units, styles, MSRP, brands in that slot, box numbers. Sorted in walk order

Two details that make them usable rather than merely correct. Brand counts belong inside the manifest — the buyer's first question is always "how much of each brand". And the bare list of location codes needs to be copyable in one action, because it gets pasted into a message to the floor.

Test to write first

sum(manifest.qty) == sum(pull_sheet.units) == sum(brand_counts.units) == lot.units. It catches key collisions, double-counting, and filter leakage in one assertion. Address columns by header name, not position — the manifest gained a column and a position-based test silently checked the wrong one.

08State & persistenceexpanded in rev 2

Start empty

The app ships with no data in it. Sheets arrive by drag-and-drop and are kept in client-side storage. Rebuilding the app must not touch what the user loaded, and must not reintroduce sheets they removed. This also took the shipped file from 2.8 MB to 100 KB.

Three states per location, per sheet

Available
In the pool, appears in results.
Staged
In the lot being built. Leaves the pool immediately, so header counts and every later search only show what's unclaimed.
Removed
Physically gone. Never reappears, including after the next data refresh.

Storage map

WhatWhereKeyed by
Staged + removed locationslocalStorage, per sheetlocation code
Hidden sheetslocalStoragesheet slug
Loaded sheet dataIndexedDBsheet slug
Key by code, never by index

Row indices shift every time the export changes; codes don't. Keep removed codes that are absent from the current export rather than pruning them — absent means shipped, not undone.

Removed state has no other copy, so ship an export and a matching import. Browser storage can be cleared.

Initialisation order — this bit twice

Both storage layers silently failed because their key constants were declared below the startup code. var hoists the name but not the value, so at startup the app read localStorage.getItem(undefined) and opened an IndexedDB database literally named "undefined". Both looked like "persistence doesn't work". Run startup last, after every definition, and the whole class of bug disappears.

09Sheet ingestion

A 4.4 MB workbook of 144,635 rows parses and cleans in about one second in the browser, with no library.

An .xlsx is a ZIP of XML. Modern browsers inflate it natively:

  1. Read the End of Central Directory record, walk the central directory, take each entry's compressed bytes from its local header offset.
  2. DecompressionStream('deflate-raw') for method 8, raw bytes for method 0. Feature-detect it and fall back to asking for CSV rather than failing obscurely.
  3. xl/sharedStrings.xml → an array; scan <si>, concatenating the <t> runs inside each.
  4. Scan the sheet XML with a stateful regex over <row> and <c>. Do not use DOMParser — the sheet here is 32 MB uncompressed.
  5. Resolve each cell by its r="AB12" reference, not by position. Empty cells are omitted entirely from the XML.
  6. Pick the tab with the most rows. Real files carry notes tabs.

Cell type matters: t="s" indexes shared strings, t="inlineStr" holds text inline, anything else is a literal in <v>. Unescape the five XML entities plus numeric character references.

Prove the two paths agree

With a server cleaner and a browser cleaner, diff them on a real file and assert field-by-field equality across every row — not just totals. Doing this surfaced four real bugs: the fabricated $45k of MSRP, the missing case-insensitive flag, a null-skipping aggregate that took a title from one product and a size from another, and a composite key joined with an empty separator. Totals alone would have hidden all four.

10Conflicts screennew in rev 2

Because nothing is merged, the app owes the user a way to see what a barcode actually means. This screen is not a nicety — it is the counterweight to rule two.

List every barcode carrying more than one product name. Click one to expand every name on it with units, share of the barcode, how many slots each sits in, and price. Grade each barcode with the same precedence the rows are labelled with, so the tallies add up:

split        runner-up is 3+ units AND 5%+ of the barcode, different brands
stray        runner-up is 1-2 units
sameBrand    all names share a brand
other        mixed brands, small numbers

Two annotations earn their place on an expanded card:

  • One price across every name. 370 of the conflicted barcodes carry a single price across an average of three products — the signature of a barcode used as a price tier rather than a product code. Worth telling the user, because it is a floor-process habit, not a data-entry typo.
  • Same brand, different names. Say explicitly that these are kept as separate products and the buyer gets exactly the line they were shown. This is where a user will otherwise assume the app has duplicated something.

Ship search across barcode, brand and name, plus a CSV export — the list is what the warehouse needs in order to fix the habit at source.

11Traps & invariants

Assert these

  • Manifest, pull sheet and brand counts agree on units.
  • Sum of stack units equals sum of input Remaining, minus explicitly reported drops. Report every drop with a reason and a count.
  • No location appears in two lots.
  • Every stack's brand, category and size derive from that stack's own title.
  • No title in the output is absent from the input.
  • One product has exactly one price across every stack.

Report quality, don't silently fix it

Every run should emit a plain-text report: what was repaired, what was dropped and why, which barcodes carry several names, what remains unidentifiable. The 38 genuinely split barcodes can't be resolved by software — but they can be handed back to the warehouse as a list, which is the only thing that actually fixes them.
